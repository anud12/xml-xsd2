## Description
Plan reference: plans/ui-div-layer.md, "The game view (ui.canvas)" section and Phase 2b
bullet 2 ("world.js (in .ui): the ui.canvas node type — world: { map, room } descriptor +
per-client camera: { room, x, y, zoom } state. Camera is ui.state-scoped so each client has
its own view; a minimap (room graph) writes the main camera state.").

Room/Portal data now exists in Rust (task 009). This task adds the CANVAS NODE to the .ui
layer: a leaf that divs host the way a page hosts <canvas>. The Godot spatial renderer
(SubViewport/Node2D/Camera2D) is the NEXT task (011); here the canvas node is declared,
evaluated, and delta-synced — the renderer side may be a stub placeholder.

Resolved open questions: world rendering v1 = static sprite per unit from room container data
(no unit animations/selection/fog); portal crossing = teleport, staged in Phase 2c (task 012).

Work items:
1. application/ui/ui/world.js (new) + host.js factory:
   - ui.canvas(id, options, world):
       options: same painting options as div where sensible (background, clip) + the canvas
         is sized/positioned by its parent div exactly like any other leaf (the div layout
         system from task 004 assigns it geometry — that is the point of the model).
       world descriptor (expressions, re-evaluated per tick): { map, room } — which (single)
         map to render and which room is ACTIVE. v1 is single-map: map may be a constant
         "world"; room is a room id (string constant, expression, or state value).
   - Per-client camera state via ui.state (task 005's state.js):
       camera: { room, x, y, zoom } — declared as ui.state slots scoped per client
       (e.g. state.declare("camera") or dedicated ui.state.camera accessors — pick one, keep
       it per-client). The canvas node's delta carries the camera snapshot so the renderer
       can place the view.
   - A minimap (room graph) is a small div whose room-node clicks call a ui.action that
     writes the main camera state (re-center onto that room). Implement the ui.action wiring
     here (the action + state mutation + next-tick delta); the minimap's visual is a plain
     div grid of room labels for v1 (the graph drawing is optional polish — do it if
     time-boxed).
2. application/ui/types/canvas.d.ts: the canvas node type, world descriptor, and camera
   shape.
3. Rust (application/runtime/src/ui/):
   - UiNode gains a Canvas kind: { id, world: { map, room }, camera: { room, x, y, zoom },
     geometry (from layout) }.
   - uiTick() resolves the world descriptor per client: look up the active room in the room
     state from task 009 (if the room id is unknown, the canvas delta carries an
     "unknown room" marker instead of crashing), and attaches a ROOM SNAPSHOT to the canvas
     node payload: the room's { origin, rotation, points } + portal list (so the renderer
     task 011 needs only the delta, no separate FFI — rooms changed at runtime automatically
     propagate because the descriptor is re-evaluated each tick).
     - Also attach, per room container: the member entity ids + their local getX/getY values
       (read from container state — the container data already carries getX/getY position
       fns evaluated at declaration; if they need per-tick re-evaluation against entity
       state, resolve them here using the same entity-value access pattern as task 005's
       field binding). This is the "units placed in the room" data for v1 static sprites.
   - Camera mutation: ui.action-registered camera setters (pan/zoom/recenter) mutate
     per-client camera state in QuickJS; the next tick's delta carries the new camera.
4. C# side (minimal, stub):
