## Title
Phase 2c (Layer B): portal crossing as a per-tick effect (teleport semantics) + room adjacency

## Description
Plan reference: plans/ui-div-layer.md, "Data Model — Phased depth" bullet B ("portal crossing
as a per-tick effect (a unit whose local position exits through a portal's edge range is moved
to the target room at the mapped local range, in the target room's local coordinates); then
room adjacency (portal-connected rooms are nav-adjacent); then pathfinding. Crossing alone
already demonstrates a live-extending map.")

Resolved open question #6: v1 crossing semantics = TELEPORT (no transition animation).

This is pure runtime (Rust/QuickJS) work — the renderer already draws whatever rooms/units the
state says (tasks 009-011), so a unit crossing a portal "just appears" in the other room.

Semantics (spell out in tests — this is the contract):
1. Per tick, for each unit in each room (units = entities whose membership + local x/y come
   from the room's container via the getX/getY maps — the same data path task 010 surfaces):
   - For each portal P whose `from.room` is the unit's room:
     - Compute the unit's position relative to edge `P.from.edge`: project the unit's local
       position onto the edge line and test (a) the unit crossed OUT of the room through that
       edge (the unit is outside the convex polygon, and the exit is through this edge — for
       v1 a simpler, deterministic rule is acceptable and must be documented: the unit's
       local position is on the outside half-plane of the edge line AND within the edge's
       segment span), and (b) the along-edge parameter t of the intersection/position is in
       [t0, t1].
     - If both hold: TELEPORT the unit — remove it from `from.room`'s container and add it to
       `to.room`'s container at the local position mapped from the `to` side: take the SAME
       t (clamped to the target range), pick a target local position just inside the target
       edge at that t (v1: the edge midpoint offset a fixed epsilon inward along the edge
       normal — document the epsilon rule), and set the unit's local getX/getY in the target
       room accordingly.
   - Camera follow (plan: "When a unit (or the camera) crosses a portal's edge range, the
     active room transitions to the portal's target — the camera follows"): if the crossed
     unit is the client's actor (or follows the camera-follow convention chosen in task 010),
     the active room / camera.room transitions to the target room via the same ui.action /
     state path the minimap uses (no new mechanism).
2. Room adjacency (same task, small): build the adjacency view (portal-connected rooms are
   nav-adjacent) as a derived structure in state (rooms.rs or a new adjacency module) — an
   API like rooms_adjacent(room_id) -> Vec<room_id>. No pathfinding (deferred per plan).
   Expose it for future use via the same fetch/FFI JSON as rooms (cheap) or a getter.
3. Implementation location:
   - Crossing check + teleport: Rust state layer (src/state/ or a new src/world/ module —
     decide and document), invoked once per runtime_run_iteration
     (src/ffi_mod/misc/run_iteration/mod.rs) after effects run (units' positions change
     during effects, so crossing must be evaluated AFTER process_pending/scheduled/behavior).
   - Container membership mutation: reuse the existing container state representation
     (LAST_CONTAINERS / the container data structures behind get_container_by_id in
     src/ffi_mod/misc/get_container_by_id.rs). If containers are stored as opaque JSON
     strings today, parse/mutate/serialize them — keep the format compatible with the
     existing C# ContainerInterop reader (application/client/solution — check the
     ContainerInterop type; do NOT change the wire format).
   - Entity position values live in LAST_ENTITY_NUMBER_DATA keyed per entity — the unit's
     local x/y maps are per (entity) number map keys; the teleport writes the target room's
     getX/getY values. Document exactly which keys are read/written.
4. Edge cases (each gets a test):
   - Unit exactly on the edge line (degenerate) — no crossing (strict outside-half-plane test).
   - t just outside [t0, t1] — no crossing; t at the boundary — crossing (decide inclusive
     vs exclusive, document, test).
   - Two portals on the same edge with disjoint ranges — the one whose range contains t wins.
   - Unit crossing out of a room that has no matching portal range — nothing happens.
   - Teleport target room is the same as source (self-loop portal) — allowed, unit stays.
   - Multiple units crossing in one tick — all processed; order deterministic (sorted by
     entity id).
   - A unit added to the target room mid-tick is NOT re-checked for crossing again in the
     same tick (no infinite ping-pong; the crossing pass runs once per tick on the
     start-of-tick membership snapshot).
