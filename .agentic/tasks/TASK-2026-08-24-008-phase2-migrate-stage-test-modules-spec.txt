Migration rules per module (derive the ui.div equivalent from the registerPanel call):
- PanelOptions.id -> ui.window or ui.div id (panels with children/absolute placement become
  windows; content-only panels become a div inside a default full-rect window — follow the
  MainModule pattern from TASK-007).
- size/offset/anchor -> window position/size + coordinate-escape (x/y + anchor/align) on the
  div, reproducing the exact screen rect the PanelOptions produced (top/bottom/left/right
  offset model -> concrete pixels).
- content types map as:
    constant / constantNumber      -> ui.text(value)
    entityTextValue                -> ui.field(id, entity, "text", name, { fallback: "" })
    entityNumberValue              -> ui.field(id, entity, "number", name, { fallback: "" })
    containerListView (template)   -> a ui.div whose children are generated per container
      entity at declaration time (the template is a JS function — call it per entity id from
      __host_getContainerEntityIds-equivalent in the QuickJS host; if the Rust host does not
      yet expose container ids to UI declaration, add a readClientState-style host function
      __uiTransport.containerEntityIds(containerId) in this task's Rust work — that part is
      agent-doable in application/runtime and should be split out as a sub-commit).
- background/hover/onClick/layout.children -> the same options on ui.div / ui.window (already
  supported after TASK-006).
- The TestClass.cs assertion files (AssertPanel etc.) live in the restricted Test/ directory:
  where they assert on legacy panel structure, the human must update assertions to the new
  node ids/types. List every TestClass.cs that will need assertion updates in the migration
  checklist (grep "HasContentText|AssertPanel" under Test/).

Deliverable (human): a branch `task/TASK-2026-08-24-008` containing the migrated modules +
